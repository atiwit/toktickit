# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Sprint นี้มีเป้าหมายเพื่อส่งมอบ MVP ของระบบ TokTickIT สำหรับฝั่ง Requester โดยสมบูรณ์ ซึ่งประกอบด้วยการสร้าง Ticket, ดูรายการ Ticket, ดูรายละเอียด Ticket, และจัดการ Attachment (อัปโหลด, ดาวน์โหลด, soft-remove) ทั้งหมดนี้ทำงานภายใต้ Zen Green Theme ที่ตอบสนอง (Responsive) ครบทุก Breakpoint พร้อม API ที่ enforce ownership อย่างเข้มงวด

---

## 2. Stakeholder Request Interpretation

Stakeholder ต้องการระบบ IT Support Ticketing ที่ให้ผู้ใช้งานฝ่าย Requester สามารถส่ง Ticket แจ้งปัญหาได้ด้วยตนเอง และสามารถ Track สถานะรวมถึงแนบไฟล์หลักฐานได้ โดยในระยะนี้ยังไม่มีระบบ Authentication จริง จึงใช้กลไก Development Requester Selection เพื่อจำลอง Context ของผู้ใช้งานสำหรับการทดสอบ ระบบต้องแยกข้อมูลของ Requester แต่ละคนออกจากกันอย่างเด็ดขาดผ่านการตรวจสอบ Ownership ในทุก API

## 3. Scope

### Included
- Development Requester Selection screen
- Create Ticket screen
- My Tickets screen
- Ticket Detail screen (view mode)
- Attachment upload, download, and soft-removal
- Zen Green Theme + responsive layout

### Excluded
- Authentication (login, sessions, tokens)
- IT Staff workflow
- Public Comments / Internal Notes / Actions Taken
- Ticket status changes beyond NEW
- Administration functions

## 4. Functional Requirements

- **FR-01** The system provides a Development Requester Selection screen; a Requester must be selected before accessing any ticket screen.
- **FR-02** The selected Requester's name is displayed in the app header with a "Change Requester" action that reloads all requester-specific data.
- **FR-03** A Requester can create an IT support ticket by filling in Category, Related System, Requested Priority, Summary, Description, and optional Attachments; the Ticket Number and Date are generated by the backend.
- **FR-04** A Requester can view a paginated list of their own tickets (My Tickets) with keyword search, filter by Status/Category/Priority, and sort by date/status/priority.
- **FR-05** A Requester can open a read-only Ticket Detail screen showing all ticket fields and a list of all attachments (active and removed).
- **FR-06** A Requester can upload an attachment (JPG/PNG/WEBP/PDF, ≤ 5 MB) to an existing ticket, subject to a maximum of 5 active attachments per ticket.
- **FR-07** A Requester can soft-remove one of their own active attachments by providing a removal reason; the metadata remains visible but the file is no longer downloadable.
- **FR-08** All ticket and attachment operations are ownership-enforced: a Requester cannot view, modify, or download resources belonging to another Requester.
- **FR-09** All screens apply the Zen Green Theme and are responsive across desktop (≥ 992 px), tablet (768–991 px), and mobile (< 768 px) viewports.

## 5. Business Rules

- **BR-01** Ticket Number and Ticket Date are generated by the backend on creation; status defaults to `NEW`; the frontend must not send or override these values.
- **BR-02** The Development Requester selector is a testing mechanism only (not authentication); only active Requesters appear in the dropdown; inactive ones are excluded.
- **BR-03** If no active Requesters exist or the API fails, the selection screen shows a clear error/empty state and blocks proceeding.
- **BR-04** The selected Requester is held in app context; switching Requester immediately reloads all requester-specific data.
- **BR-05** A Requester may only access their own Tickets and Attachments; any cross-requester access returns HTTP 403 with no data leaked.
- **BR-06** Required fields — Summary (max 200 chars), Description (max 2000 chars), Category, Related System, Requested Priority — are validated on both frontend (field-level messages below each field) and backend (400 + field details) independently.
- **BR-07** Requested Priority must be one of: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`. All string fields are trimmed of leading/trailing whitespace before validation and saving.
- **BR-08** The Submit button is disabled and shows a busy state while in-flight (prevents double-submit); on API failure all form values are preserved.
- **BR-09** If a Ticket is saved but an attachment upload subsequently fails, the Ticket is kept and only the attachment error is shown — no rollback.
- **BR-10** My Tickets searches `summary` and `ticketNumber` (case-insensitive partial match); supports simultaneous filters (Status, Category, Priority); default sort is Created Date descending; pagination is 1-based, default 10 per page (allowed: 10, 25, 50); API returns `totalCount`, `totalPages`, `currentPage`, `pageSize`.
- **BR-11** My Tickets shows an empty-state when no tickets exist, and a distinct no-results state (with Clear Filters action) when search/filter returns nothing.
- **BR-12** Allowed attachment types: JPG/JPEG, PNG, WEBP, PDF; max size 5 MB per file; max 5 active attachments per Ticket.
- **BR-13** Attachment removal is soft-only: set `isRemoved = true`, record a non-empty `removedReason` (max 500 chars) and `removedAt`; the record is never deleted.
- **BR-14** A removed Attachment remains visible as metadata but its download link/button must not be rendered.
- **BR-15** Attachment files are stored server-side with a UUID-based filename; the original filename is kept as metadata only.
- **BR-16** The Ticket Detail screen is fully read-only; no edit controls, Comments, Internal Notes, Actions Taken, or status-change UI may appear.
- **BR-17** All screens must be responsive (desktop ≥ 992 px, tablet 768–991 px, mobile < 768 px) with no horizontal scroll, clipping, or hidden controls at any breakpoint.
- **BR-18** The `RequesterUser` model is temporary; the schema must be designed so that replacing it with a real `User` model in Lab 3 does not require data loss.

## 7. Data Changes

### Models

| Model | คำอธิบาย |
|---|---|
| `RequesterUser` | ผู้ใช้งานชั่วคราวสำหรับ Dev (Lab 2 เท่านั้น) ประกอบด้วย `id`, `name`, `email`, `isActive` |
| `Category` | Reference data สำหรับหมวดหมู่ Ticket มี `isActive` flag |
| `RelatedSystem` | Reference data สำหรับระบบที่เกี่ยวข้อง มี `isActive` flag |
| `Ticket` | หน่วยหลัก ประกอบด้วย `ticketNumber` (unique, backend-generated), `status` (default `NEW`), `requestedPriority`, `summary`, `description` และ FK ไปยัง `RequesterUser`, `Category`, `RelatedSystem` |
| `Attachment` | ไฟล์แนบ ประกอบด้วย `originalFilename`, `storedFilename` (UUID-based), `mimeType`, `size`, `isRemoved`, `removedReason`, `removedAt` |

### Enums

| Enum | Values |
|---|---|
| `Priority` | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `TicketStatus` | `NEW`, `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED` |

### Indexes

- `Ticket`: index บน `requesterId`, `status`, `ticketNumber` (รองรับ BR-10 query pattern)
- `Attachment`: index บน `ticketId`

### การออกแบบเพื่อรองรับ Lab 3 (BR-18)

`Ticket.requesterId` เป็น FK ชี้ไปที่ `RequesterUser.id` เท่านั้น การเปลี่ยนเป็น `User` model จริงใน Lab 3 ต้องการเพียง migration เปลี่ยน FK target โดยไม่ต้อง migrate ข้อมูล Ticket

## 8. API Contract

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | Health check |
| GET | `/api/requesters` | List active Development Requesters |
| GET | `/api/categories` | List active Categories |
| GET | `/api/related-systems` | List active Related Systems |
| POST | `/api/tickets` | Create a Ticket |
| GET | `/api/tickets` | List owned Tickets (paginated + search/filter/sort) |
| GET | `/api/tickets/:id` | Get one owned Ticket detail |
| POST | `/api/tickets/:id/attachments` | Upload Attachment |
| GET | `/api/tickets/:id/attachments` | List Attachment metadata |
| GET | `/api/attachments/:id/download` | Download active Attachment |
| DELETE | `/api/attachments/:id` | Soft-remove an Attachment |

Requester identity ส่งผ่าน HTTP Header `X-Requester-Id: <id>` ในทุก request ที่ต้องการ ownership check

รายละเอียด Request/Response shape ครบถ้วนอยู่ใน [`api-spec.md`](./api-spec.md)

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data, when submitted, then a Ticket is saved and the Ticket Number is displayed.
- **AC-02** Given no Requester is selected, when navigating to a protected screen, then the Requester Selection screen is shown.
- **AC-03** Given Requester B is selected, when requesting a Ticket owned by Requester A, then 403 is returned.
- **AC-04** Given a Ticket with 5 active attachments, when uploading another file, then 400 is returned with an appropriate error message.
- **AC-05** Given a valid attachment, when soft-removing with a reason, then `isRemoved = true` and the download button disappears.
- **AC-06** Given the My Tickets screen, when searching by keyword, then only matching tickets are shown; when no results, the no-results state with Clear Filters is displayed.
- **AC-07** Given any screen, when viewed on mobile (< 768 px), then no horizontal scroll occurs.

## 11. Assumptions and Decisions

- **Ticket Number Format:** ใช้รูปแบบ `TKT-YYYYMMDD-NNNN` (เช่น `TKT-20260901-0001`) โดย NNNN reset เป็น 0001 ทุกวัน — ตัดสินใจนี้เพื่อให้ Ticket Number อ่านง่ายและระบุวันที่สร้างได้ทันที
- **Requester Identity Header:** ใช้ `X-Requester-Id` header (หรือ query param fallback) แทน session/token เพราะยังไม่มี Auth ใน Lab 2 — ออกแบบให้เปลี่ยนได้ง่ายใน Lab 3
- **Soft-remove endpoint:** ใช้ `DELETE /api/attachments/:id` (ไม่ใช่ PATCH) เพราะ semantics ของ HTTP DELETE ตรงกับ "ลบ" แม้การลบจะเป็น soft-delete ก็ตาม
- **Attachment Cleanup:** เมื่อ upload ล้มเหลวหลังจาก ticket ถูก save แล้ว (BR-09) ไฟล์ที่อยู่บน disk จะถูก cleanup ด้วย `fs.unlinkSync` แต่ ticket ถูก keep ไว้
- **My Tickets sort:** ปัจจุบัน sort รองรับ `date_asc` / `date_desc` (default) เท่านั้น เพราะ frontend ใช้ Created Date เป็นหลัก
