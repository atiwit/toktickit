## 3. Scope

### Included
- Development Requester Selection screen
- Create Ticket screen
- My Tickets screen

- Attachment upload, download, and soft-removal
- Zen Green Theme + responsive layout

- IT Staff workflow
- Public Comments / Internal Notes / Actions Taken

- Administration functions

## 4. Functional Requirements

- **FR-01** The system provides a Development Requester Selection screen; a Requester must be selected before accessing any ticket screen.
- **FR-02** The selected Requester's name is displayed in the app header with a "Change Requester" action that reloads all requester-specific data.
- **FR-03** A Requester can create an IT support ticket by filling in Category, Related System, Requested Priority, Summary, Description, and optional Attachments; the Ticket Number and Date are generated by the backend.
- **FR-04** A Requester can view a paginated list of their own tickets (My Tickets) with keyword search, filter by Status/Category/Priority, and sort by date/status/priority.
- **FR-05** A Requester can open a read-only Ticket Detail screen showing all ticket fields and a list of all attachments (active and removed).
- **FR-06** A Requester can upload an attachment (JPG/PNG/WEBP/PDF, ≤ 5 MB) to an existing ticket, subject to a maximum of 5 active attachments per ticket.
- **FR-07** A Requester can soft-remove one of their own active attachments by providing a removal reason; the metadata remains visible but the file is no longer downloadable.
- **FR-08** All ticket and attachment operations are ownership-enforced: a Requester cannot view, modify, or download resources belonging to another Requester.
- **FR-09** All screens apply the Zen Green Theme and are responsive across desktop (≥ 992 px), tablet (768–991 px), and mobile (< 768 px) viewports.

## 5. Business Rules

- **BR-01** Ticket Number and Ticket Date are generated by the backend on creation; status defaults to `NEW`; the frontend must not send or override these values.
- **BR-02** The Development Requester selector is a testing mechanism only (not authentication); only active Requesters appear in the dropdown; inactive ones are excluded.
- **BR-03** If no active Requesters exist or the API fails, the selection screen shows a clear error/empty state and blocks proceeding.
- **BR-04** The selected Requester is held in app context; switching Requester immediately reloads all requester-specific data.
- **BR-05** A Requester may only access their own Tickets and Attachments; any cross-requester access returns HTTP 403 with no data leaked.
- **BR-06** Required fields — Summary (max 200 chars), Description (max 2000 chars), Category, Related System, Requested Priority — are validated on both frontend (field-level messages below each field) and backend (400 + field details) independently.
- **BR-07** Requested Priority must be one of: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`. All string fields are trimmed of leading/trailing whitespace before validation and saving.
- **BR-08** The Submit button is disabled and shows a busy state while in-flight (prevents double-submit); on API failure all form values are preserved.
- **BR-09** If a Ticket is saved but an attachment upload subsequently fails, the Ticket is kept and only the attachment error is shown — no rollback.
- **BR-10** My Tickets searches `summary` and `ticketNumber` (case-insensitive partial match); supports simultaneous filters (Status, Category, Priority); default sort is Created Date descending; pagination is 1-based, default 10 per page (allowed: 10, 25, 50); API returns `totalCount`, `totalPages`, `currentPage`, `pageSize`.
- **BR-11** My Tickets shows an empty-state when no tickets exist, and a distinct no-results state (with Clear Filters action) when search/filter returns nothing.
- **BR-12** Allowed attachment types: JPG/JPEG, PNG, WEBP, PDF; max size 5 MB per file; max 5 active attachments per Ticket.
- **BR-13** Attachment removal is soft-only: set `isRemoved = true`, record a non-empty `removedReason` (max 500 chars) and `removedAt`; the record is never deleted.
- **BR-14** A removed Attachment remains visible as metadata but its download link/button must not be rendered.
- **BR-15** Attachment files are stored server-side with a UUID-based filename; the original filename is kept as metadata only.
- **BR-16** The Ticket Detail screen is fully read-only; no edit controls, Comments, Internal Notes, Actions Taken, or status-change UI may appear.
- **BR-17** All screens must be responsive (desktop ≥ 992 px, tablet 768–991 px, mobile < 768 px) with no horizontal scroll, clipping, or hidden controls at any breakpoint.
- **BR-18** The `RequesterUser` model is temporary; the schema must be designed so that replacing it with a real `User` model in Lab 3 does not require data loss.
